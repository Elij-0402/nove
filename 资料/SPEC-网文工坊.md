# SPEC：网文工坊 —— 对标蒸馏式网文创作 skill 工作流

状态：ready-for-agent（本地 spec，无 issue tracker）
来源：`资料/deep-research-report (1).md` + grilling 会话（Q1–Q32）

## Problem Statement

我是独立网文作者，每次写新书都会找一本同类型的热门爆款做对标，希望借它的成功经验写出超越原作的新作。现在的做法全靠对话里临时发挥，问题有这些：

- 拆书靠印象。说不清爆款到底"爆"在哪里，也就说不清新作该往哪个方向超越原作。
- 让 AI"模仿某某文风"只能学到表面，写出来的东西 AI 腔很重，读者一看就出戏。
- 长篇连载写到几十、上百章以后，境界、持有物、伏笔、人际关系的前后一致全靠人记，很容易吃书。
- 每次隔几天回来接着写，都要重新交代项目背景和进度。
- 对标时读过原文，写的时候容易无意识地复刻原作桥段，有洗稿风险。
- 手上那份方法论报告有模板和步骤，但落不了地：里面提到的 GPTZero、LangChain 这类工具在 Claude Code 里用不上，"去 AI 化"的示例本身就是 AI 腔，长篇一致性问题也没有涉及。

## Solution

在这个工作区里搭一套项目级 skill，由 1 个总控和 6 个阶段 skill 组成，全部用中文写，把"对标爆款 → 拆解蒸馏 → 写出超越原作的新作"固化成一条可以反复使用的流水线：

- **拆书**：把对标源本拆成爆款模型、基线指标和风格档案。机械指标用脚本实测，语义指标由 Claude 判断；重点找出原作的弱点，作为新作超越的突破口。
- **立项**：基于拆书结果给出 3 个差异化方案，由我拍板。
- **设定、大纲**：按报告里的模板建作品库，角色卡增加"当前状态"栏，大纲阶段做原创性自检。
- **写章**：支持三种模式，分别是代写、收稿和局部代笔。写之前只读取相关内容，写完后回写状态。
- **审稿**：4 个维度并行检查，自动返修最多 2 轮。
- **总控**：读取项目状态，告诉我现在在哪一步，并在人工关卡之外自动推进。

对标只借鉴抽象层（结构、节奏、情绪点模型、钩子手法、人设原型、金手指机制、文风数据），新作的人物、世界和情节全部原创。

## User Stories

### 总控与项目状态

1. 作为作者，我想输入 `/novel` 就看到当前所有作品的进度和下一步建议，这样隔几天回来也能直接接上。
2. 作为作者，我想让总控在人工关卡之外自动调用下一个阶段的 skill，这样不用每步都手动输入命令。
3. 作为作者，我想让总控在立项、总纲、每卷卷纲、每一章完成后都停下来等我确认，这样方向性的决定始终由我来做。
4. 作为作者，我想让项目进度只记录在一个状态文件里，这样进度不会出现两个互相矛盾的版本。
5. 作为作者，我想在状态文件里看到每个关卡的决定记录（我选了什么、为什么），这样之后可以回溯当时的思路。
6. 作为作者，我想同时管理多部作品，总控能分别告诉我每部的进度。
7. 作为作者，我想单独调用任何一个阶段 skill（比如只拆一本书），不必每次走完整流程。
8. 作为作者，我想在工作区里闲聊时不被误触发 skill，这样聊天和干活互不干扰。

### 拆书

9. 作为作者，我想把下载来的 txt 丢进对标库，拆书 skill 能自动识别 UTF-8、UTF-8 BOM、GBK/GB18030 编码，这样不用自己转码。
10. 作为作者，我想让拆书自动清掉下载站的声明、广告和分隔线，这样这些杂质不会污染指标。
11. 作为作者，我想让拆书能识别常见的章节标题格式（"第N章"、中文数字、番外、卷标题），并正确切分章节。
12. 作为作者，我想精拆开篇（前 15 万字或前 50 章，取较少的一方），黄金三章逐章拆解，这样最能决定读者留存的部分被看得最细。
13. 作为作者，我想让全书按卷粗拆（每卷的主冲突、换地图时机、升级或关系推进曲线），这样我能看清宏观节奏。
14. 作为作者，我想让长篇拆书交给子代理分块并行处理，这样几百万字的书也能在合理时间内拆完。
15. 作为作者，我想让拆书报告用一句话说清核心卖点，这样我能判断这本书爆的根本原因。
16. 作为作者，我想让情绪点（爽点、甜点、虐点等）的类型库按这本书的题材归纳出来，不套用固定的玄幻爽点表，这样言情、都市、悬疑等题材都能拆。
17. 作为作者，我想让每种情绪点都附上常用的铺垫手法，这样我能学到"怎么把它铺出来"，不只是"它是什么"。
18. 作为作者，我想让拆书分析章末钩子的手法和类型分布，这样我能学到让读者追读的办法。
19. 作为作者，我想让拆书按功能定位（主角、主要配角、反派或情敌）提炼人设原型，不照搬具体人物。
20. 作为作者，我想让拆书分析金手指或核心设定的机制，以及它的展示节奏。
21. 作为作者，我想让拆书专门列出原作的弱点（读者常吐槽的地方、拖沓的段落、逻辑硬伤），这样新作有明确的超越方向。
22. 作为作者，我想得到一份用脚本实测的基线指标（章长、对白占比、句长和段长分布、高频词），以及 Claude 判断的语义指标（情绪点间隔、大高潮间隔、钩子覆盖率、新角色引入频率、主角高光间隔），这样新作有可以量化对比的尺子。
23. 作为作者，我想得到一份风格档案（叙述视角、句长和段长分布、描写与叙事的比例、高频词和口头禅、标志性修辞，以及该作者从不用的表达），这样"文风"从一句形容词变成可以检查的约束。
24. 作为作者，我想把拆书产物存在对标库里，同一本书以后给别的新作用时不必重拆。
25. 作为作者，我想让拆书只输出抽象层的内容，不输出原作的情节对照表，这样从源头降低洗稿风险。

### 立项

26. 作为作者，我想让立项一次给出 3 个方案，每个方案包含一句话卖点、针对原作弱点的超越点、与对标作品的差异清单、目标平台和篇幅，这样我可以比较着选。
27. 作为作者，我想能选其中一个方案，或者要求把几个方案合并，这样最终方向由我决定。
28. 作为作者，我想指定 1 本主对标和 1～2 本辅助对标，并写明每本辅助对标借鉴的是哪一项（比如开局节奏、金手指机制），这样新作是"A 的骨架加上 B 的亮点"。
29. 作为作者，我想让基线指标以主对标为准，这样对比的尺子只有一把。
30. 作为作者，我想让平台和每章字数在立项时按项目记录下来，这样审稿基线和读者画像都跟着这个平台走。
31. 作为作者，我想让新作的风格档案从对标的风格档案派生，再按新作的需要调整，这样既有数据依据，又不会变成复刻。

### 设定

32. 作为作者，我想按报告里的模板生成角色、世界观、势力、力量体系（或关系体系）和时间线，这样设定结构统一、方便查找。
33. 作为作者，我想让每张角色卡都有"当前状态"栏（境界或身份、所在地、持有物、伤势、人际关系），这样长篇连载时状态可以追踪。
34. 作为作者，我想让设定按类别分开存放，这样写某一章时只需读取相关文件。
35. 作为作者，我想让 Claude 在生成设定后检查设定内部的矛盾，这样问题在动笔前就被发现。

### 大纲

36. 作为作者，我想得到"总纲 → 卷纲 → 章纲"三层大纲，这样宏观和微观节奏都可控。
37. 作为作者，我想让大纲参照对标的情绪点间隔和高潮间隔来排布节奏，这样新作的节奏不低于基线。
38. 作为作者，我想维护一张伏笔表（埋设章节、计划回收章节、状态），这样伏笔不会被遗忘。
39. 作为作者，我想让总纲和卷纲在交给我之前先做原创性自检：与对标的拆书报告比对，标出情节层面的重合（相同的桥段组合、相同的人物关系结构）并改掉，这样避免无意识复刻原作。
40. 作为作者，我想让总纲和每卷卷纲都停下来等我确认，这样故事方向由我掌控。

### 写章

41. 作为作者，我想让 Claude 按章纲代写章节初稿，这样我可以把主要精力放在把关和修改上。
42. 作为作者，我想让代写前自动读取本章章纲、相关伏笔、出场角色的角色卡、全书摘要、当前卷摘要和前 2～3 章原文，这样上下文够用但不会爆炸。
43. 作为作者，我想让代写时遵守项目的风格档案，并主动避开 AI 腔清单里的写法，这样初稿质量更高。
44. 作为作者，我想把自己写好的章节放进正文目录，由 skill 收稿：回写状态、摘要和伏笔，然后送审，这样我自己写的章节也能进入同一条流水线。
45. 作为作者，我想请 Claude 局部代笔（"这场戏帮我写"、"补一段过渡"、"这段重写"），这样卡文时有人帮一把。
46. 作为作者，我想让每写完一章都自动回写角色当前状态、伏笔表、时间线和卷摘要，这样作品库始终是最新的。
47. 作为作者，我想让每卷写完后把卷摘要压缩进全书摘要，这样上下文不会随章数增长而膨胀。
48. 作为作者，我想让章节按统一的编号命名存放，这样顺序清楚、方便引用。
49. 作为作者，我想让章节字数符合项目设定的每章字数，这样符合平台习惯。

### 审稿

50. 作为作者，我想让每章完成后跑一次轻审（一致性、AI 腔、字数），这样每一章都有基本的质量保证。
51. 作为作者，我想让每 5 章，以及黄金三章的每一章，都跑一次全审（在轻审基础上加上基线对比和读者盲评），这样节奏类指标在有意义的窗口上测量。
52. 作为作者，我想让轻审的停顿频率和全审间隔可以在项目状态文件里调整，这样风格稳定后我可以放宽。
53. 作为作者，我想让一致性检查核对正文与设定、角色当前状态、伏笔表是否一致，并抽查回写的状态是否正确，这样回写的错误不会累积下去。
54. 作为作者，我想让 AI 腔检查按规范里的 AI 腔清单逐条标出问题并给出改写，这样去 AI 腔是可检查的，不是凭感觉。
55. 作为作者，我想让 AI 腔检查参照风格档案的白名单（原作者常用的词不算 AI 腔），这样不会误伤文风。
56. 作为作者，我想让基线对比用和拆书同一个脚本来测新作，这样两边的数字可以直接比较。
57. 作为作者，我想让读者盲评子代理看不到设定和大纲，只读正文，这样它的反应接近真实读者。
58. 作为作者，我想让盲评按平台的读者画像来评，输出弃书点、跳读点、吐槽点和追读意愿分（1–10），这样我知道真实读者会在哪里流失。
59. 作为作者，我想让 4 个审稿维度并行执行，每个子代理只拿到它需要的材料，这样又快又能相互隔离。
60. 作为作者，我想让审稿不通过时由 Claude 按问题清单自动返修，最多 2 轮，还不通过就停下来交给我判断，这样机械性问题自动解决，方向性问题由我决定。
61. 作为作者，我想让每次审稿产出一份报告，列出问题、返修记录和本次改动的状态，这样我扫一眼就知道这批章节的质量。

### 规范与工作区

62. 作为作者，我想把 AI 腔清单放在工作区的规范目录里，看到新的 AI 腔可以直接加一条，所有项目随即生效。
63. 作为作者，我想把设定模板放在规范目录里，我可以按自己的习惯修改。
64. 作为作者，我想把读者画像（第一版包括番茄、起点、晋江）放在规范目录里，以后遇到新平台可以自己补充。
65. 作为作者，我想让工作区里有一份简短的 CLAUDE.md，说明这是写作工作区、入口是 `/novel`，这样每次开新会话 Claude 都知道该从哪里开始。
66. 作为作者，我想让工作区里已有的 25 个工程类 skill 保持不动，这样不影响我在别的场景使用它们。

## Implementation Decisions

### 模块（7 个 skill + 1 个脚本 + 规范）

skill 装在项目级 skills 目录。name 用拼音加 `novel-` 前缀，description 和正文都用中文，7 个都允许模型自动调用：

| skill | 职责 | 读 | 写 |
|---|---|---|---|
| `novel` | 总控：读取项目状态，给出进度和下一步，在关卡之外调度其他 skill | 项目.md | 项目.md（状态推进） |
| `novel-chaishu` | 拆书 | 对标源本 | 拆书报告、基线指标、风格档案（存入对标库） |
| `novel-lixiang` | 立项：3 个方案 → 人工关卡 | 对标库产物 | 项目.md、项目风格档案 |
| `novel-sheding` | 设定 | 立项结果、规范/模板 | 设定/* |
| `novel-dagang` | 总纲、卷纲、章纲、伏笔表，以及原创性自检 | 设定、对标拆书报告 | 大纲/* |
| `novel-xiezhang` | 写章：代写、收稿、局部代笔三种模式，写后回写 | 章纲、伏笔、角色卡、摘要、前 2～3 章、风格档案、AI 腔清单 | 正文、角色当前状态、伏笔表、时间线、摘要 |
| `novel-shengao` | 审稿：4 个并行子代理，自动返修 ≤2 轮 | 视维度而定（见下） | 审稿/批次报告 |

- skill 的写法遵循工作区已有 skill 的惯例：主 SKILL.md 保持简短，只在部分分支用到的内容拆到同目录的大写子文件里；每条规则以一句加粗的短句开头；用词始终统一。
- 不生成给 OpenAI 用的 `agents/openai.yaml`，这套 skill 只在 Claude Code 里使用。

### 作品库结构（数据契约）

```
<工作区>/
├─ 对标库/<书名>/   原文.txt  拆书报告.md  基线指标.md  风格档案.md  指标.json
├─ 作品/<书名>/
│   ├─ 项目.md        ← 唯一的进度来源
│   ├─ 风格档案.md
│   ├─ 立项方案.md    ← 立项的候选方案存档
│   ├─ 设定/  角色.md 世界观.md 势力.md 力量体系.md 时间线.md
│   ├─ 大纲/  总纲.md 卷纲-NN.md 伏笔表.md
│   ├─ 正文/  NNNN-章名.md
│   ├─ 摘要/  全书摘要.md 卷摘要-NN.md
│   └─ 审稿/  批次-NNN.md
├─ 规范/  AI腔清单.md  读者画像.md  模板/
└─ 资料/  方法论报告、本 spec
```

- 拆书产物和新作分开存放，一本对标书拆一次，可以给多部新作复用。
- 立项方案待拍板时放在 `作品/立项方案-<主对标>.md`，拍板后移进作品目录，改名 `立项方案.md`。项目.md 在拍板后才创建。
- 力量体系对言情等题材改为"关系体系"，由设定 skill 按题材选择。

### 项目状态机（项目.md）

阶段按顺序推进，★ 表示人工关卡：

`拆书 → 立项★ → 设定 → 总纲★ → 卷纲★ → 写章（每章★）→ 卷末结算（卷摘要并入全书摘要）→ 下一卷卷纲★ …`

项目.md 至少记录这些字段：书名、平台、每章目标字数、主对标和辅助对标（以及各自借鉴的项）、当前阶段、当前卷和当前章、停顿频率（默认 1 章）、全审间隔（默认 5 章，前 3 章每章都全审）、关卡决定日志。

### 指标脚本（唯一的确定性模块）

- 用 Python 标准库实现，放在 `novel-chaishu` 的 scripts 目录下，拆书和审稿共用。
- 输入：一个 txt 文件，或一个章节 md 目录。输出：一份 JSON。同一输入必须得到完全相同的输出。
- 职责：识别编码（UTF-8 / UTF-8 BOM / GB18030）；剥离站点声明和分隔线杂质；按章节标题切分（"第N章"、中文数字、番外、卷标题）；统计每章和全书的字数、对白占比（引号内字数与总字数之比）、句长和段长分布、高频词。
- JSON 的形状：一个全书汇总对象，加一个每章数组。每章记录序号、标题、字数、对白占比、句长统计、段长统计。
- 不做语义判断。情绪点、钩子、高光这类指标由 Claude 在拆书和审稿时判断。

### 拆书策略

- 精拆范围是前 15 万字或前 50 章，取较少的一方，黄金三章始终逐章拆；其余部分按卷粗拆。
- 超过一定体量的书，分块交给子代理并行处理，由主代理汇总。
- 情绪点类型库按题材归纳，不预设玄幻爽点表。
- "弱点"是拆书报告的必填项，是立项时确定超越点的输入。
- 只输出抽象层内容，不输出原作的逐章情节对照。

### 一致性策略

- 写之前按需读取：本章章纲、相关伏笔、出场角色的角色卡、全书摘要、当前卷摘要、前 2～3 章原文。
- 写之后回写：角色当前状态、伏笔表、时间线、卷摘要。卷末把卷摘要压缩进全书摘要。
- 回写可能出错，由审稿的一致性维度抽查纠正。

### 审稿

- **轻审（每章）**：一致性、AI 腔、字数。
- **全审（每 5 章，前 3 章每章都做）**：在轻审基础上加基线对比（脚本测最近窗口，加语义指标对比）和读者盲评。
- 各维度由独立子代理并行执行，每个只拿到自己需要的材料：
  - 一致性：正文、设定、伏笔表、角色卡。
  - AI 腔：正文、AI 腔清单、风格档案白名单。
  - 基线对比：脚本输出、对标基线。
  - 读者盲评：**只有正文和读者画像**。
- 不通过时自动返修，最多 2 轮，然后复审；仍不通过就停下来交给我。

### 原创性护栏

- 拆书阶段：只输出抽象层内容。
- 大纲阶段：总纲和卷纲要与对标拆书报告比对，标出情节层面的重合（桥段组合、人物关系结构），改掉之后再提交关卡。

### 规范（初始内容由搭建者撰写，之后由作者维护）

- **AI 腔清单**：逐条可检查，每条包含特征、示例和改法。覆盖比喻泛滥（仿佛、宛如、如同……一般）、四字词堆砌、情绪直接说出来、对称的段落结构、高频套话（不由得、嘴角微微上扬、眼中闪过一丝）、总结式段尾、排比滥用等。方法论报告中"改进后"的那个示例本身就是 AI 腔，收作反例。
- **读者画像**：番茄（免费读者，耐心低）、起点（付费老读者，讨厌降智和水字数）、晋江（言情读者，看重感情线逻辑、人设不 OOC、甜虐节奏）。
- **模板**：报告中的 8 张表，角色卡增加"当前状态"栏，力量体系和关系体系二选一。

## Testing Decisions

- **好的测试只测外部行为**：给定输入文件，检查输出的 JSON 和产物文件，不测内部函数。
- **接缝 1：指标脚本的命令行接口（自动化测试）**。用 Python 标准库 unittest 编写，以《难哄》源本为主要夹具：
  - 切出 89 章（含番外）。
  - 输出中不含下载站声明文字。
  - 同一份文本分别存成 UTF-8、UTF-8 BOM、GB18030 三种编码，输出完全一致。
  - 同一输入跑两次，输出逐字节相同。
  - 抽 3 章人工核对字数和对白占比，误差在容差范围内（字数 ±1%，对白占比 ±3 个百分点）。
  - 输入章节目录与输入单个 txt，对同样的内容得到一致的统计结果。
- **接缝 2：端到端试跑（人工验收，不做自动化）**。用《难哄》走完拆书 → 立项 → 设定 → 大纲 → 写 3 章 → 审稿，按清单检查：
  - 每个阶段的产物文件是否齐全、符合作品库结构。
  - 项目.md 的状态是否按状态机推进。
  - 立项、总纲、卷纲、每一章这几个关卡是否真的停下来。
  - 拆书报告是否没有原作情节对照；情绪点类型库是否是言情题材的（而不是玄幻爽点表）。
  - 原创性自检是否实际执行并有记录。
  - 读者盲评子代理的输入里是否确实没有设定和大纲。
  - 前 3 章是否每章都做了全审；审稿报告里是否有返修记录。
- 试跑中暴露的衔接问题（上游产物格式下游读不懂等）修复一轮，之后再交付。
- 先例：工作区现有的都是工程类 skill，没有可以参照的写作类测试，这是第一套。
